Enhancement category 1

Software Design and Engineering

Restructuring two all-in-one screens into a layered, testable design, and adding the features an inventory app needs.

What changed

In the original, each activity read input, built display strings, ran SQL, and read database cursors. I separated those responsibilities so each class has one job, which makes the code easier to read, change, and test.

MainActivity ──────┐                         ┌── ValidationUtils (input rules, pure Java)
                   ├── uses ─────────────────┤
InventoryActivity ─┘                         ├── DatabaseHelper (all SQL, migration, timing)
       │                                     │        └── PasswordHasher (salt + PBKDF2)
       └── InventoryAdapter ── shows ──> InventoryItem (id, name, quantity)
  • UI layer: MainActivity, InventoryActivity, InventoryAdapter. No SQL and no cursors.
  • Logic layer: ValidationUtils, PasswordHasher. No Android dependencies, so they run in plain JUnit tests.
  • Data layer: DatabaseHelper returns InventoryItem objects and simple results.

Before and after: adding an item

The original passed raw text straight to Integer.parseInt, so an empty quantity crashed the app. The enhanced version validates first, shows the error on the field, and confirms the save.

New functionality

  • Edit an item: tap an item to open a dialog prefilled with its name and quantity. The dialog stays open with an error if the input is invalid.
  • Safer delete: long-press asks for confirmation first.
  • Clearer screens: on-screen instructions, an empty-list message, and an "out of stock" label for zero quantities.
  • Maintainability: all user-facing text moved into strings.xml; every cursor is closed.

Testing

I replaced the empty template test with 31 JUnit tests in ValidationUtilsTest and PasswordHasherTest. All 31 pass with JUnit 4.13.2. The enhancement notes also include 18 manual emulator test cases; their results have not yet been recorded, so they are not reported as passed.

Skills demonstrated

  • Separation of concerns and the model and adapter pattern in Android
  • Refactoring working code without losing behavior or data
  • Designing for testability and writing automated unit tests
  • Responding to instructor feedback with an architecture diagram, pseudocode, and a documented test plan
