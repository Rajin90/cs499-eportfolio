Artifact Narrative

1. Artifact Description

The artifact for my ePortfolio is my Inventory Management Application, which I originally built in CS 360, Mobile Architecture and Programming, in Spring 2026. It is an Android application written in Java that stores data in a local SQLite database. Users can register an account, log in, and manage a list of inventory items. The original version could add items, list them, and delete them with a long-press.

I enhanced this application in Milestone Two of CS 499. The course guidelines allow a single artifact to represent all three enhancement categories, and this enhancement changed the application at every layer: its design, its core logic and data structures, and its database. This narrative explains the work in each category. The original source code, the enhanced source code, a README, and detailed enhancement notes are included with the artifact.

2. Justification for Inclusion

I chose this project because it touches most of what a real application needs: a user interface, user authentication, persistent storage, and create, read, update, and delete operations. When I reviewed the code for this course, I also found real weaknesses, including a delete bug, plain-text passwords, a crash on empty input, and no database upgrade path. That made it a strong artifact for showing that I can take working code, evaluate it critically, and improve it, which is much of what professional developers do. My Module One plan named three goals: improve the user experience, reorganize the code for maintainability, and add useful functionality. The enhancements below follow those goals.

Software Design and Engineering

  • Layered architecture. In the original, both activities did everything: read input, build display strings, run database calls, and read cursors. I separated the application into layers. An InventoryItem model represents one record, an InventoryAdapter handles display, ValidationUtils holds every input rule, PasswordHasher handles password security, and DatabaseHelper is the only class that contains SQL.

  • Testability. ValidationUtils and PasswordHasher have no Android dependencies, so I could write plain JUnit tests for them. I added 31 unit tests to replace the default template test, and all 31 pass with JUnit 4.13.2.

  • New functionality. Tapping an item now opens an edit dialog prefilled with its name and quantity, and the dialog stays open with an error message if the input is invalid. I also added a delete confirmation, an out-of-stock label, on-screen instructions, and an empty-list message.

  • Maintainability. All user-facing text moved from hard-coded strings into strings.xml, and every database cursor is now closed, which fixes a resource leak.

Algorithms and Data Structures

  • Fixing a bug at the data-structure level. The original deleted items using the list position plus one as the database ID. Once any item was deleted, IDs had gaps, so a long-press could delete a different item or nothing at all. The cause was a data-structure decision: the list stored display strings and discarded each record's ID. I replaced that list of strings with a list of InventoryItem objects that keep their real IDs, and both update and delete now target the row by ID.

  • Validation logic. Each validation method checks its rules in a fixed order, such as required, then length, then allowed characters, and returns a specific message for the first rule that fails. Invalid data is stopped before it reaches the database, and the user sees exactly which field to correct. The original crashed with a NumberFormatException on an empty or non-numeric quantity.

  • Algorithm selection and trade-offs. I chose PBKDF2 with HMAC-SHA256, a 16-byte random salt per user, and 120,000 iterations. The iteration count deliberately makes each login slower, because the same cost makes stolen hashes expensive to crack. Hashes are compared in constant time so the comparison does not leak timing information. I documented this speed-versus-security trade-off and added timing logs so its cost can be measured.

  • Pseudocode. I documented registration, login, and the add, update, and delete workflows as pseudocode, which is included in the enhancement notes.

Databases

  • Schema version 2 with constraints. Usernames are now required and unique without regard to case, item names are required, and quantity cannot be negative. The database enforces these rules itself, so invalid data is rejected even if a future screen forgets to validate it. Passwords are stored as a hash and salt instead of plain text.

  • Migration. The original onUpgrade method was empty, so any schema change would have broken existing installations. I wrote a version 1 to version 2 migration that hashes existing passwords, drops blank accounts, keeps the first account when usernames are duplicated, and repairs invalid item rows while keeping their original IDs. I tested the migration SQL against deliberately messy version 1 data, and the new constraints rejected invalid inserts.

  • Query design. I added an index on item name that matches the case-insensitive ordering of the item list, kept every query parameterized (the original already passed user input as selection arguments, and every new query follows the same pattern), and made update and delete report whether exactly one row changed.

  • Measurement. In response to my Module One feedback, every database operation logs its elapsed time to Logcat under the tag CS499_DB_PERF, and the enhancement notes include a table for recording averages. The logging is implemented, but the averages have not yet been recorded, so this narrative does not report measured performance results.

To support PBKDF2 and the standard Base64 encoder, I raised the minimum Android version from API 24 to API 26 (Android 8.0). This was a deliberate trade-off: a small number of very old devices lose support in exchange for a standard, secure hashing algorithm.

3. Reflection on the Enhancement Process

The biggest thing I learned is that reading old code critically is a separate skill from writing code that works. When I wrote this app in CS 360, it passed my own testing, so I assumed it was correct. Looking at it again, I found a delete bug that only shows up after an item has been removed, because the list position and the database ID stop lining up. It was a design problem, not a typo. I had thrown away the ID when I turned each record into a display string. Fixing it meant changing how data moves through the app, which is why I added the InventoryItem model instead of patching one line.

Another lesson was that changing a database is more than changing the CREATE TABLE statement. Because the original onUpgrade method was empty, anyone who already had the app installed would have kept the old schema. Writing the migration made me think about the bad data the old version allowed, such as blank names, duplicate usernames, and negative quantities, and decide what should happen to each.

The main challenge was balancing security against compatibility and speed. Secure password hashing required a higher minimum Android version and is expected to make login noticeably slower than other operations. I decided both costs were acceptable and documented why, so the decision can be reviewed rather than hidden. One known limitation remains: password hashing currently runs on the user-interface thread, and moving it to a background thread is the next improvement I would make. The manual emulator test cases in my enhancement notes are written but their results have not yet been recorded, so I report only the automated unit test results here.

4. Feedback Incorporated

My Module One feedback asked for exact architecture changes, performance measurements, the database schema, test cases, pseudocode or a flowchart, and a mapping to course outcomes. I addressed each item: the enhancement notes include a before-and-after architecture diagram, both schema versions, pseudocode, unit and manual test cases, and an outcome mapping, and the code now logs the elapsed time of each database operation. The timing logs make performance measurable, but the measured averages are still to be recorded. In my status checkpoint I also asked my instructor for feedback on two decisions, raising the minimum Android version and my approach to migrating existing user data, because those were the trade-offs I was least certain about.
