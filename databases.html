Enhancement category 3

Databases

Moving the SQLite schema to a constrained version 2, migrating existing data safely, and keeping all SQL in one parameterized data layer.

Schema: version 1 and version 2

  • Constraints in the database itself: required usernames that are unique regardless of case, required item names, and CHECK (quantity >= 0). Invalid data is rejected even if a future screen forgets to validate it.
  • No plain-text passwords: only password_hash and salt are stored.
  • Index: idx_items_name uses the same case-insensitive collation as the item list's ORDER BY.

Migration from version 1

The original onUpgrade was empty, so any schema change would have left existing installs on the old tables. The enhanced version migrates existing data inside the upgrade transaction.

  • Users: each old password is replaced by a salted hash; blank accounts are dropped; for duplicate usernames, the first account is kept.
  • Items: all rows keep their original IDs; blank names become "Unnamed item"; missing or negative quantities become 0.
  • Verified: the migration SQL was tested against deliberately messy version 1 data (duplicates, blanks, a negative quantity, ID gaps), and the new constraints rejected invalid inserts.

Data access layer

  • All SQL lives in DatabaseHelper; the activities never build queries or read cursors.
  • Every query uses parameterized selection arguments ("username = ?"), never string concatenation of user input.
  • Every cursor is closed with try-with-resources, fixing the original resource leak.
  • Each operation logs its elapsed time to Logcat under CS499_DB_PERF, added in response to Module One feedback. The logging is implemented; measured averages have not yet been recorded.

Skills demonstrated

  • Relational schema design with integrity constraints and indexing
  • Planning and writing a data migration for existing users
  • Secure data storage and injection-resistant queries
  • Instrumenting database operations so performance can be measured
