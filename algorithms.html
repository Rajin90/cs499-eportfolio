Enhancement category 2

Algorithms and Data Structures

Fixing a bug at its source by changing a data structure, writing predictable validation logic, and making a deliberate algorithmic trade-off between speed and security.

Scope note. This category is supported by the algorithm and data-structure changes made within the same enhancement of the CS 360 app. A separate algorithms milestone was not completed, so this outcome is reported as partially met.

1. The delete bug was a data-structure problem

The original list held display strings like "Apples - Qty: 5", which threw away each record's database ID. Delete then guessed the ID from the list position. After any deletion, IDs have gaps (for example 1, 3, 4), so long-pressing the second row deleted ID 2, which no longer existed, or deleted the wrong item.

The fix replaced ArrayList<String> with a list of InventoryItem objects that keep their real ID. Update and delete now target the exact row by primary key, and both report whether exactly one row changed. Fixing the data structure removed the whole class of bug instead of patching one line.

2. Ordered validation logic

Each rule is checked in a fixed order, and the method returns the first failure as a user-facing message, or null when the input is valid. Invalid data never reaches the database, and the user sees exactly what to correct.

public static String validateQuantity(String quantityText) {
    String value = quantityText == null ? "" : quantityText.trim();
    if (value.isEmpty()) {
        return "Quantity is required";
    }
    int quantity;
    try {
        quantity = Integer.parseInt(value);
    } catch (NumberFormatException e) {
        return "Quantity must be a whole number";
    }
    if (quantity < 0) {
        return "Quantity cannot be negative";
    }
    if (quantity > QUANTITY_MAX) {
        return "Quantity cannot be more than " + QUANTITY_MAX;
    }
    return null;
    }

3. Choosing an algorithm for its cost

The original compared plain-text passwords inside a SQL query. The enhanced app uses PBKDF2-HMAC-SHA256 with a random 16-byte salt per user and 120,000 iterations, then compares hashes in constant time.

  • Trade-off: the iteration count makes each login deliberately slow (the enhancement notes expect hundreds of milliseconds; averages have not yet been recorded), because the same cost makes every guess against a stolen hash expensive. It is acceptable because it happens once per login.
  • Constant-time comparison: MessageDigest.isEqual checks every byte, so response time does not reveal how much of a guess matched.
  • Measured, not guessed: registerUser and authenticate log elapsed time under CS499_DB_PERF.
  • Known limitation: hashing runs on the UI thread; moving it to a background thread is the next improvement.

4. Deterministic migration rules and pseudocode

The version 1 to 2 migration processes accounts in ID order and keeps the first account when a username is duplicated, so the result is predictable. Each workflow (register, log in, add, update, delete) is documented as pseudocode in the enhancement notes.

Skills demonstrated

  • Tracing a defect to its data-structure root cause
  • Selecting an algorithm by its cost characteristics and documenting the trade-off
  • Writing deterministic, testable decision logic
  • Using pseudocode to segment functionality before coding
