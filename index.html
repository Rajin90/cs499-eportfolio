Professional Self-Assessment

Professional Self-Assessment (Word)

Introduction

I became interested in computer science after watching family members use technology in their work and daily lives, which made me curious about how the software behind it was built. I started the Bachelor of Science in Computer Science at Southern New Hampshire University wanting to become a software developer. I still have that goal, but the program, and the CS 499 capstone in particular, has given me a much clearer picture of what kind of developer I want to be. This self-assessment introduces the skills and values I developed in the program, explains how they prepare me for professional work, and introduces the artifacts that follow in this ePortfolio.

Growth, Values, and Professional Goals

Early in the program I thought of programming mainly as getting code to run. Courses such as CS 360, Mobile Architecture and Programming, where I built an Android inventory application, and CS 465, where I worked on a MEAN-stack project, showed me that I enjoy building complete applications that real users interact with. The capstone changed my thinking the most. When I returned to my CS 360 application, I found a delete bug, plain-text passwords, and code that would be hard to maintain, even though the app had passed my own testing when I first wrote it. That experience showed me that professional work is less about writing new code and more about reading, improving, and securing code that already exists.

Two values guide how I work. The first is accuracy: documentation should describe what the code actually does, and limitations should be visible to the people who depend on it. In my enhancement notes, for example, I recorded the automated test results I had actually run and left the emulator test results blank until they are run, rather than reporting outcomes I had not observed. The second is responsibility for the people who use and maintain software. That means validating input, protecting user data, and leaving code organized well enough that the next developer can understand it.

My immediate goal is an entry-level software engineering role, or a mobile or full-stack developer position, where I can keep growing in design, testing, and security rather than only building features. After gaining hands-on experience, I plan to pursue a certification such as AWS Certified Developer – Associate, and I may consider a master's degree in computer science once I know which area I want to specialize in.

Program Outcomes and Professional Skills

Collaborating in a Team Environment

Software is built and maintained by teams, and team decisions depend on accurate, accessible information. In the capstone I treated my instructor as a stakeholder in my design decisions. My Module One feedback asked for performance measurements and test cases, and I responded directly in my Milestone Two enhancement by adding timing logs for every database operation, writing a documented test plan, and replacing the default template test with 31 unit tests. In my status checkpoint, I also asked for feedback on two specific design decisions: raising the minimum Android version to support secure password hashing, and the approach I used to migrate existing user data. Asking targeted questions about trade-offs, instead of asking only whether the work is acceptable, is how I want to take part in design discussions on a team.

I also support collaboration through documentation that lets other people work with my code without needing me present: a README with setup and test instructions, enhancement notes with a before-and-after comparison, schema, and pseudocode, and comments that explain why a decision was made. The capstone also included a recorded code review, a common collaborative practice in software development. After discussing this requirement with my instructor, I decided to proceed without the recording. I recognize that this leaves my portfolio with less direct evidence of review-based collaboration. Giving and receiving structured code reviews is a skill I intend to keep developing in a professional setting.

Communicating with Stakeholders

The capstone required me to explain the same technical work to different audiences. My narratives are written for an evaluator who wants to understand my reasoning and the outcomes addressed. My README is written for a developer who needs to open, run, and test the project. My journals were written with a recruiter in mind, explaining how I would present a specific example, such as the delete bug I found and fixed, during an interview. Writing for each audience taught me to lead with purpose and impact and then give the technical detail to the readers who need it. This ePortfolio applies the same principle: each artifact page summarizes the work in plain language first and provides code and documents for readers who want to go deeper.

Algorithms and Data Structures

Algorithm design is about trade-offs, and the capstone made those trade-offs concrete. In my CS 360 enhancement, I deliberately chose a password-hashing algorithm, PBKDF2, that repeats its work 120,000 times. That makes logging in slower by design, because the same cost makes stolen password hashes expensive to crack, and I documented that decision and how to measure its impact. I also traced the delete bug to a data-structure decision: the original list stored display strings and discarded each record's database ID. Replacing those strings with model objects that keep their real IDs fixed the bug at its source instead of patching the symptom.

The same thinking applies to everyday logic. My validation rules check every input in a fixed order and return a specific message for the first rule that fails, so the user knows exactly what to correct and invalid data never reaches the database. My data migration processes existing accounts in a defined order and keeps the first account when it finds a duplicate username, which makes the result predictable. Outside this artifact, my work in CS 370 with an intelligent agent that used reinforcement learning showed me a different kind of algorithmic thinking, where a program's behavior depends on how well its learning process is designed and evaluated, not only on whether the code runs.

Software Engineering and Databases

My Milestone Two enhancement turned the CS 360 Inventory Management Application from two activities that did everything into a layered design. Each class now has one responsibility: a model class represents an inventory record, an adapter handles display, a validation class holds every input rule, a password class handles hashing, and a single database helper contains all SQL. Because the validation and hashing classes have no Android dependencies, I was able to test them with plain JUnit tests. I also added item editing, delete confirmation, clear error messages on each field, and a fix for a crash caused by an empty quantity.

On the database side, I moved the schema to a second version with constraints that enforce required fields, unique usernames, and non-negative quantities. Because the original upgrade method was empty, I wrote a migration that converts existing data, hashing old passwords and repairing invalid rows while keeping their IDs. I added an index to support the application's sorted item list, kept every query parameterized, and closed every database cursor to fix a resource leak. That work taught me that changing a database means planning for the data that already exists, not only rewriting the table definition. Outside this artifact, my CS 465 full-stack project used the MEAN stack, whose MongoDB document database stores data very differently from the relational SQLite tables in this application.

Security

The capstone gave me a security mindset that I now apply when reading any code: I ask how input could be misused, what an attacker could learn from stored data or error messages, and what happens when an operation fails. In my CS 360 enhancement, that led me to replace plain-text password storage with salted PBKDF2 hashing and a constant-time comparison, mask the password field, keep every database query parameterized, enforce constraints in the database as well as in the user interface, and show the same login error for an unknown username and a wrong password so the screen does not reveal which accounts exist.

I also apply this mindset to how I share work. While packaging my CS 360 project for this portfolio, I noticed that a local configuration file contained my Windows username in a file path, so I removed it before sharing the project. Before publishing to GitHub, I review projects for credentials, personal information, test accounts, and configuration files that should not be public. Security is not only a feature of the code, but part of how a developer handles everything around it.

Portfolio Overview

This self-assessment is the first section of my ePortfolio. The portfolio is built around one artifact, my CS 360 Inventory Management Application, which the course guidelines allow to represent all three enhancement categories. It is followed by an artifact page with the original and enhanced source code and my artifact narrative, one page for each enhancement category, a program outcome map, and a code review page that explains the status of that requirement.

The three category pages look at the same application from different angles. The software design and engineering page shows how I restructured two all-in-one activities into a layered, testable design and added features users need. The algorithms and data structures page shows how a data-structure change fixed the delete bug at its source, how my validation logic works, and the deliberate speed-versus-security trade-off behind password hashing. The databases page shows the version 1 and version 2 schemas side by side, the constraints and index I added, and the migration that converts existing data. Because one artifact connects all three, a reader can see how a single design decision in one layer affects the others.

Together, the pages move from user-facing application design, through algorithmic reasoning, to secure data persistence. The common thread is the approach I want to bring to a professional team: evaluate existing work honestly, make changes for clear and measurable reasons, test what I build, and document the result so that others can understand, trust, and extend it.

Conclusion

The Computer Science program gave me practical experience across software design, algorithms, databases, and security, and the capstone taught me how to apply that experience to code that already exists, which is where much of professional development work happens. I am preparing for an entry-level software engineering role with a clear sense of what I do well and what I still want to develop, and this portfolio is the foundation I will continue to build on.
